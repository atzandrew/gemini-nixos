# USB networking — the gadget is CDC-ECM, and the Mac can drive the cycle

Last updated: 2026-09-17

Status: 🟡 **config built + host scripts changed — not flashed, not on
glass.**
The device's USB NIC moved from RNDIS to **CDC-ECM** so that **macOS**
(which has no RNDIS driver at all) can use the same 10.15.19.82 link the
Linux workstation uses — and the host scripts that drive the reboot/flash
cycle now run on both platforms. The kernel change is a **boot.img
reflash** (`bash bin/build.sh start bootimg` → `bash bin/flash-nixos.sh
boot`), which has **not** happened; the image below is built, verified
against the boot contract, and sitting in the artifact cache. **No rootfs
change is involved** — the device-side side of the link (usb0 =
10.15.19.82, static, in `config/gemini.nix`) is untouched, so `boot`
alone carries this change.

Read with: `bin/lib/host.sh` (the host-side code), the cheat sheet in
`AGENTS.md`, `docs/macos-build.md` (the Mac build half),
`docs/disaster-recovery/` (recovery).

## Why this change exists

The 2026-09-12 analysis (`docs/session-log.md`) found the one platform
block in the Mac workflow: the device enumerated as **`0525:a4a2`, the
Linux RNDIS gadget**, and **macOS ships no RNDIS driver** (only
CDC-ECM/NCM; HoRNDIS is an unmaintained kext and is not an option on
Apple Silicon). The recommendation was exactly what is implemented here:
*"switch the gadget to CDC-ECM (kernel config + boot.img reflash)"*.

CDC-ECM is natively driven by **both** hosts this repo supports:

| Host | Driver | Evidence |
|---|---|---|
| Linux | `cdc_ether` (usbnet) | generic match on class 2/subclass 6; the gadget's `0525:a4a1` is the NetChip "Linux-USB Ethernet Gadget" id |
| macOS | `com.apple.driver.usb.cdc.ecm` (`AppleUSBECM.kext`) | personalities match `IOUSBHostInterface` class 2/subclass 6 → `AppleUSBECMControl`, class 10 → `AppleUSBECMData`; **verified present + loaded** on the M5 (macOS 26.6.2, `kmutil showloaded`) — exactly the descriptor set `f_ecm` emits |

RNDIS, by contrast, serves Linux + Windows only. Windows is not a host
this repo has, and macOS — the host this change is *for* — cannot use it.
So the trade is deliberate: **ECM (Linux + macOS) instead of RNDIS
(Linux + Windows)**.

> Windows, if it ever matters: the kernel keeps the configfs **NCM**
> function (`CONFIG_USB_CONFIGFS_NCM=y`) for that. It is *not* wired up —
> the precomposed `g_ether` gadget used here has no NCM option, and a
> configfs gadget needs a userspace binder service (see "Why not
> configfs" below).

## What changed, exactly

### Device (kernel config)

`CONFIG_USB_ETH_RNDIS` is now **off** (plus `CONFIG_USB_CONFIGFS_RNDIS`
and the promptless `CONFIG_USB_F_RNDIS`, which only those two select).
Generated by `bin/prune-kernel-config.sh` **section 9c** — re-run that
after any config regeneration, or the symbol comes back with the #329
base (`config.full-329` still carries it as `=y`, deliberately: it is
the A/B reference).

Why the symbol matters (`drivers/usb/gadget/legacy/ether.c`, v6.6 — the
source the in-repo kernel is built from):

```c
	/* register our configuration(s); RNDIS first, if it's used */
	if (has_rndis()) {
		status = usb_add_config(cdev, &rndis_config_driver,
				rndis_do_config);
		...
	}
	status = usb_add_config(cdev, &eth_config_driver, eth_do_config);
```

- **RNDIS on** → two configurations, RNDIS registered first, so every
  host picks it; the device descriptor is overridden to
  `0525:a4a2` (`RNDIS_PRODUCT_NUM`, "Ethernet/RNDIS Gadget").
  That is the `0525:a4a2` the 2026-09-12 analysis measured.
- **RNDIS off** → exactly **one** configuration, the CDC-ECM one
  (`eth_config_driver`, `bConfigurationValue = 1`), with the NetChip
  ids `0525:a4a1` (`CDC_PRODUCT_NUM`, "Linux-USB Ethernet Gadget") and
  `bDeviceClass = USB_CLASS_COMM`.

Everything else about the gadget is unchanged: it is still the
**precomposed `g_ether`** (`CONFIG_USB_ETH=y`), still auto-instantiates,
still takes its MACs from the `g_ether.dev_addr` / `g_ether.host_addr`
kernel params, still appears as **`usb0`**, and still comes up whenever
the mtu3 UDC appears — no userspace involvement.

### Host (Linux + macOS)

New shared library **`bin/lib/host.sh`** holds the platform differences so
they exist once, not five times:

| Concern | Linux | macOS |
|---|---|---|
| find the NIC | `ip -o link` matching the gadget MAC | `ifconfig -a` matching it (then `networksetup -listallhardwareports`) |
| configure it | `ip link set` + `ip addr replace 10.15.19.1/24` | `ifconfig <if> inet 10.15.19.1 netmask 255.255.255.0 up` |
| ping the device | `ping -c1 -W <seconds>` | `ping -c1 -W <milliseconds>` |
| USB ids (`lsusb`) | `lsusb` | `system_profiler SPUSBDataType` (best-effort; no usbutils on darwin) |
| adb + `timeout`/`stat -c` | flake devshell | flake devshell (`flake-macos.nix`) |

**Interface discovery is by MAC, not by name.** The host end of the link
is `42:00:15:19:82:00` (the `g_ether.host_addr` param), which reaches the
host inside the ECM functional descriptor (Linux's `cdc_ether` and macOS's
`AppleUSBCDCECMData` both adopt it), so matching `42:00:15:19:82:`
finds the interface whatever USB port it lands in — no more
`enp10s0f4u1u2`. `GEMINI_USB_IFACE=<iface>` overrides the search, and
`GEMINI_DEV_IP=<ip>` still reaches the device over Wi-Fi/LAN exactly as
before.

Scripts updated (all keep their Linux behaviour; `bin/lib/host.sh` is
sourced where needed):

| Script | What changed |
|---|---|
| `bin/net-up.sh` | `ifconfig` on macOS; MAC-based interface discovery; platform ping |
| `bin/device-ssh.sh` | same; `GEMINI_DEV_IP` override preserved (link setup skipped for it) |
| `bin/device-reboot.sh` | **no `lsusb` any more** — the WDT-reset is proved by the link/ssh dropping and by the boot_id change; the address is re-applied from the lib after re-enumeration |
| `bin/boot-switch.sh` | devshell re-exec via the lib; `state()`/`status` USB probes via the lib |
| `bin/flash-nixos.sh` | same; the post-WDT "TWRP appeared" wait is now **adb-based** (was `lsusb | grep 18d1:4ee2`); artifact defaults fall back to the Mac cache dir |
| `bin/usb-watch.sh` | VID map updated (`0525:a4a1`); bus read via the lib |
| `bin/repartition-nixos.sh` | same probe conversion (it no longer hard-fails on a host without `lsusb`); artifact defaults follow the platform. Still a Linux-host tool **by policy** — see below |
| `bin/macos/vm-build.sh` | the collector now also publishes the conventional `boot.img` / `system.img` names the flash scripts default to (store paths are hash-prefixed) |
| `bin/lib/host.sh` (`gemini_ssh_key`) | every host script's key default moved from `~/.ssh/id_ed25519_gemini` to the **repo's** `keys/gemini_ed25519`, and the helper tightens a fresh clone's 0644 → 0600 (also `bin/deploy.sh`, `bin/gemshell-dev.sh`) |

## The Mac cycle, end to end

```sh
bash bin/build.sh start bootimg     # build in the aarch64 VM (docs/macos-build.md)
bash bin/build.sh wait  bootimg     # rc 0 ok / 1 failed / 2 running
bash bin/flash-nixos.sh preflight   # READ-ONLY: is a flash possible? (below)
bash bin/flash-nixos.sh status      # state + artifacts (auto-uses ~/.cache/gemini-macos/out)
bash bin/flash-nixos.sh boot        # -> TWRP (via the USB NIC ssh hop) + flash boot.img
bash bin/flash-nixos.sh boot-nixos  # clear para + reboot into it
bash bin/device-ssh.sh 'uname -a'   # back on the USB link
```

`preflight` is the readiness gate: **it touches nothing on the device** and
checks, in order — the artifact set (and *verifies every artifact against
the build's `.sha256` ledger*, which is the rule-0 "the copy we flash is
the bytes the build produced" check), the two `boot.img` cmdline fields
that matter (`bootopt=64S3,32N2,64N2` = the LK hang trap;
`fbcon=rotate:3` = the rule-5 build), the toolchain (adb + GNU coreutils),
the SSH key, sudo, and the device state if one is attached — then prints
what is missing and whether a flash can run. Exit code is non-zero only
when a **required** prerequisite is missing (a missing rootfs image or SSH
key is a warning: neither is needed for a `boot` flash).

- `bin/flash-nixos.sh` and `bin/boot-switch.sh` re-exec themselves into
  the flake's **darwin devshell** for `adb` + GNU coreutils
  (`flake-macos.nix`; `bin/lib/host.sh`'s `gemini_need_devshell`), so
  Homebrew or the Xcode CLT are not required.
- **Nothing to copy for SSH any more**: the admin key is committed at
  `keys/gemini_ed25519` and the device declares it, so a fresh clone can
  log in and flash with no provisioning (`bin/lib/host.sh` tightens a
  fresh clone's 0644 to 0600 automatically; `keys/README.md` has the
  rationale and the accepted security trade).
- **`sudo -v` once per shell** is still needed: macOS `sudo` timestamps
  are per-tty, and the first gadget-drop of a cycle has to re-apply
  `10.15.19.1` (the scripts print a hint when they cannot).

### The SSH identity lives in the repo — and is the host key too

The device's identity is part of the repo, not of this or that host's
`~/.ssh` (2026-09-17):

| | |
|---|---|
| Login key | `keys/gemini_ed25519` — declared for root + cjdell in `config/gemini.nix` (`authorizedKeys.keyFiles`), so a from-scratch reflash needs **no** manual key provisioning |
| Host key | the **same** key, installed as `/etc/ssh/ssh_host_ed25519_key` (0600) by an activation script, with `services.openssh.hostKeys` pinned to that one entry |
| Verification | `keys/known_hosts` carries its public half for `10.15.19.82`, so `ssh -o UserKnownHostsFile=keys/known_hosts root@10.15.19.82` verifies against the repo |

The point of pinning the **host** key is that a generated one changes on
every install — which is exactly what produces `REMOTE HOST
IDENTIFICATION HAS CHANGED` (and stale `known_hosts` lines) after
reinstalling from scratch. Pinned, the device's identity is stable for
the life of the key: reflash as often as you like, no warning, no
cleanup. `bin/flash-nixos.sh preflight` checks that `keys/known_hosts`
still matches `keys/gemini_ed25519.pub`, so the two cannot silently drift.

Two consequences to know:

- `hostKeys` replaces NixOS's default `[rsa, ed25519]` list, so the device
offers **ed25519 only** (every OpenSSH since 6.5 is fine);
- the private key is in git **and** in the world-readable nix store (the
activation script installs *from* a store path — the only way to get a
0600 copy; `environment.etc` would be a symlink to a 0444 file and sshd
refuses those). Deliberate: security is not a concern for this single-user
lab device — `keys/README.md` states when that must be revisited.

The scripts themselves keep `StrictHostKeyChecking=no` +
`UserKnownHostsFile=/dev/null` (as they always had): a flash must never be
blocked by host-key state, and with the pinned key the steady state is
clean anyway.

### Still not possible from a Mac

- **Preloader/BROM recovery** — `bin/run-mtk.sh` needs the Linux
  devshell's patched `mtkclient`, and Apple's `container` has no USB
  passthrough (2026-09-12 analysis, unchanged). That stays the
  last-resort Linux-host capability.
- **Exact preloader/POC/BROM detection** — macOS has no `usbutils`;
  `state()` sees those buses only if `system_profiler` reports them. The
  states the pipeline actually needs (`linux` / `twrp` / `offline`) are
  exact, because they come from ping/ssh/adb.
- `bin/run-mtk.sh` stays a Linux-host tool (above). `bin/repartition-nixos.sh`
  is Linux-host by **policy**, not by mechanism: it is a one-way
  destructive operation that has only ever been rehearsed from the Linux
  workstation, and a Mac has no preloader/BROM path if it goes wrong. Its
  probes do work on macOS now.

## Why not configfs (or NCM) in the gadget?

A configfs gadget would let the NIC function be switched at runtime
(`ecm.usb0` / `ncm.usb0`) and is the modern idiom. It was **not** chosen
because `usb0` is this unit's only network debug path:

- The precomposed gadget binds the UDC by itself, in kernel context, at
  the moment the role/cable switch presents it. A configfs gadget needs
  a userspace service that waits for `/sys/class/udc/...` and then binds
  — an ordering failure there costs the link (and therefore ssh into the
  device), which is a strictly worse failure mode than "the Mac cannot
  see the NIC" (what the RNDIS gadget gave us).
- Legacy-ECM also fails *safe*: if `can_support_ecm(gadget)` were false
  the driver silently falls back to CDC Subset (`049f:505a`, Linux-only)
  — degraded for the Mac, still fine for Linux. The kernel config keeps
  `CONFIG_USB_F_ECM=y` so the ECM path is compiled in.
- Nothing here is lost: `CONFIG_USB_CONFIGFS=m` + the ECM/NCM/EEM
  functions stay in the config, so a configfs gadget remains a small,
  additive follow-up.

## Verification (owed — needs the boot.img above flashed)

On glass, after flashing the new `boot.img`:

1. `lsusb | grep 0525` on the Linux host → must show **`0525:a4a1`**
   (ECM). `0525:a4a2` = the old RNDIS gadget (image not updated);
   `049f:505a` = the CDC-Subset fallback (ECM rejected — then revisit).
2. `bash bin/net-up.sh` → `OK: 10.15.19.82 reachable`, and
   `bash bin/device-ssh.sh 'uname -a'` works with no name hardcoding.
3. macOS: `ifconfig -a | grep -A3 'ether 42:00:15:19:82'` shows the
   interface, then `bash bin/device-ssh.sh 'uname -a'` (after `sudo -v`).
4. `bash bin/device-reboot.sh` → link drops, device comes back with a new
   `boot_id`.
5. `dmesg` on the device: `g_ether` probe messages, and on the host
   `dmesg | grep cdc_ether` (Linux) — no RNDIS mentions.

The kernel change touches **no display code** (golden rule 5 is not
involved), but it *is* a boot.img, so the usual flash safety applies:
flash with `para = boot-recovery` (the default), keep the boot backup in
`stock-dump/`, and `bin/boot-switch.sh restore` rolls back.

### Rollback

1. Re-enable `CONFIG_USB_ETH_RNDIS=y` in
   `devices/planet-geminipda/kernel/config` (**and** remove it from
   section 9c of `bin/prune-kernel-config.sh`, or the next regeneration
   re-disables it), rebuild, reflash `boot`.
2. Or boot the previous `boot.img` — the pre-change build is kept in the
   artifact cache as `gman244d9xaikqw2gzrc2nr90fw103gp-…-boot.img`
   (sha256 `b2404b13…`) and the Linux build's `stock-dump/` boot backups
   are still the authority for a device-side rollback
   (`bin/boot-switch.sh restore`). That restores `0525:a4a2` and the
   Linux-only link, with no rebuild.
